# ADR-0005: Bounded mobile avatars with transactional storage

- Status: accepted implementation decision for new mobile avatars; legacy media import remains gated
- Date: 2026-10-25
- Context: the source mobile avatar route returns a public `/api/uploads/avatars/...` URL and saves it to the authenticated role identity. Its source storage is remote and persistent; the rewrite must not reproduce earlier ephemeral-file loss or accept arbitrary upload bytes. No existing storage credentials or exported media are available in this development environment.
- Decision: store one sanitized, bounded JPEG per mobile identity in PostgreSQL, behind an application port. Save the bytes, new opaque content-addressed URL, own identity update time and audit in one transaction after fresh identity/admin checks. Replacement replaces the current row, so this slice has no unbounded object retention or external storage/metadata partial failure. Retain imported legacy avatar URLs until an explicitly verified replacement or import. This is a bounded-avatar decision, not a general image/video storage design.
- Validation: accept at most 5 MiB, decode supported JPEG/PNG/WebP/GIF, bound input dimensions/pixels and concurrent native decodes, apply orientation, flatten transparency and rebuild a static JPEG from fresh pixels without source metadata. Limit the output to 1024 × 1024 and 1 MiB. Declared MIME and filename alone cannot validate a file. No DB locks are held during decoding; the final write rechecks current authorization under row locks.
- Dependency: pin MIT-licensed SkiaSharp and its matching Linux NoDependencies assets at 4.153.1. The official [release notes](https://mono.github.io/SkiaSharp/docs/releases/4.153.1.html) disable RAW/DNG; the [pinned package guide](https://github.com/mono/SkiaSharp/blob/v4.153.1/documentation/dev/packages.md) covers server native assets. Native parsing remains an attack surface: managed cancellation cannot interrupt native decoding, and NuGet auditing does not prove the absence of native vulnerabilities. See the upstream [dependency guidance](https://github.com/mono/SkiaSharp/blob/v4.153.1/documentation/dev/dependencies.md).
- Delivery: only the exact generated avatar path can resolve these bytes. Public mobile-avatar delivery preserves the source cache and security header contract. It does not publish a social profile, set `approved_avatar_url`, grant roster access or expose private attachments. Replaced URLs return 404 at the server; immutable browser/CDN copies can remain until cache expiry, as in the source public-avatar contract.
- Consequences: small avatars share database durability/backup and atomicity. They add database/WAL/backup volume; output and one-current-row bounds limit that cost. Full PostgreSQL and legacy media restoration still requires a cutover rehearsal. Existing large media/provider keys, private social media, approval and durable processing jobs need their own mapped implementation and migration.
- Alternatives: ephemeral application files lose uploads on replacement; a new paid storage service requires separate approval; generic object storage introduces an external write/metadata failure boundary before its adapter and recovery tooling are ready. ImageSharp's newer licensing was not selected; hand-written image parsing is not maintainable.
- Revisit when: measured database/backup cost, shared media lifecycle or a verified existing provider adapter justifies moving bounded avatar bytes. Preserve URLs and explicit migration/recovery semantics during such a change.
