# POS cashier, payment, receipt and refund ledger — draft release gate

Target: **Lefteria FC OS only**. Original `Lefteria-FC` production and public/mobile payment paths are unchanged.

## Added in this slice

- Private, organization-scoped `pos.locations`, registers, cashier assignments and one-open-shift-per-register records. No public or mobile grants.
- Per-location variant stock with nonnegative/reserved bounds and a version field.
- Idempotent sale identity `(organization_id,request_id)`, immutable-intended line snapshots, server-side exact product/category/variant/name/cost/price checks, quantity constraints and EUR-cent arithmetic.
- Payments carry `cash` or `card`, pending/verified/failed states. Card verification requires provider payment ID and evidence digest; an order intent is not capture. A payment cannot exceed sale total. The eventual API must verify Payabl webhooks and reconcile external settlement **server-side**; never trust browser redirect, callback form values or parent role.
- A sale may transition to `paid` only when verified payment events equal its total and line snapshots equal its subtotal. Receipt insert requires the paid sale, exact register, verified payment total and receipt payload total. Numbering table/uniqueness make a future atomic per-register receipt issuer possible.
- Return quantities are bounded against the original sale line, including earlier pending/approved/refunded returns. Refunds must point to verified original payment on the same sale, with the same payment method, and cannot exceed captured amount or returned-line value. Pending refund confirmation has a guarded transition and requires evidence for card refunds.
- Audit table and immutable financial-history triggers; private default-deny RLS without runtime grants; rollback refuses to drop populated sale, receipt and refund data.
- Structural regression test `frontend/tests/pos-cashier-ledger-foundation.test.mjs`, disposable PostgreSQL script `ops/postgres/pos-cashier-ledger-checks.sql` and CI wiring.

## What is **not** operational yet

**This migration is a secure schema foundation, not a finished POS.** It does NOT enable checkout, authorize a cashier session, deduct inventory, verify a provider webhook, issue official tax/legal receipts, or transfer/refund funds. No runtime role can insert a sale or receipt under the new schema. Building a UI that claims otherwise is prohibited.

The next implementation gates before enabling checkout:

1. Cashier identity / two-factor, explicit register and location assignment, shift open/close and cash reconciliation, including revocation mid-session.
2. Approved product tax/VAT policy, location inventory reconciliation, stock reservations and atomic stock deduction/restocking with retry/idempotency. A browser-supplied tax/discount/total never has authority.
3. Atomic `create_cash_sale` transaction that locks stock, prices from current catalog, validates cashier shift, records counted cash evidence, assigns receipt number under lock, writes fiscal receipt payload and immutable audit, all-or-nothing.
4. Card `pending` sales followed by a separately authenticated, signature-verified Payabl capture/settlement event; failed/unpaid orders issue **no receipt**. Duplicate or out-of-order provider events must be replay-safe. Authorization/redirect is not capture.
5. Approved returns with sale-line quantity limits and separate cash refund counts/card refund provider confirmation, restocking decision, credit note/refund receipt, audit and finance reconciliation.
6. Manager POS UI, operator screen, location stock count, shift report, receipt print/PDF download and source UI parity.
7. Independent security audit; real .NET build, PostgreSQL lifecycle/rollback/negative tests, receipt fiscal/legal review for Cyprus, OpenAPI/client generation, SvelteKit tests, full CI at exact SHA and explicit release sign-off.

**Safety:** Never deploy to live, turn on payment buttons or grant runtime POS writes from this PR until these gates pass. Node source assertions are not runtime/database proof.

## Verified receipt finalization gate (additional implementation)

Migration `20261110152000_PosVerifiedReceiptIssuer` adds a private, revocation-aware SQL function for **already verified**, fully reconciled sales. It locks the exact sale, rejects incomplete/unverified payment, checks current management organization grants, allocates a register-scoped sequence under row lock, snapshots itemized line/amounts and fiscal-policy version, hashes the immutable receipt payload, appends security audit and returns the existing receipt upon replay. A disabled-by-default, owner-only `pos.receipt_policies` row is required; migration creates no enabled policy and provides **no runtime execute grant**.

This is a receipt-issuance building block, **not live legal/fiscal authorization**: tax/VAT treatment, policy approval, receipt PDF/printing, provider settlement and cashier checkout remain unimplemented and must be separately verified. No receipt is issued merely because a browser requested a payment link.

## Cashier register and cash shift slice — 2026-11-10

Added migration `20261110153000_PosCashierShiftOperations`:
- Secure database functions `pos.read_admin_cashier_registers`, `pos.open_admin_cashier_shift` and `pos.close_admin_cashier_shift`, plus a non-granted private authority helper. The caller must be a current management admin with the exact organization grant, an explicitly active cashier assignment, and active register/location. Opening/closing requests use unique UUID idempotency keys and append `pos.transaction_audit`.
- One open shift per register is enforced by the existing unique partial index. Opening cash and counted closing cash are fixed EUR cents, each capped at €1,000,000; a close records expected cash and cash variance. Expected cash equals opening cash + verified cash sales − verified cash refunds for that shift, and refuses unresolved sale/refund transactions.
- Added protected manager routes `GET /api/admin/pos/cashier/registers`, `POST /api/admin/pos/cashier/registers/{registerId}/shifts`, and `POST /api/admin/pos/cashier/shifts/{shiftId}/close`; organization, role, `shop:write` and session are rechecked by HTTP and SQL.
- Added `AdminPosCashierShiftsPanel.svelte`, integrated into the existing `/admin/pos` page, showing only verified assigned registers. It supports opening balance input, deliberate counted close and privacy-safe refresh; no cashier checkout, receipt print, card capture or sales are activated.
- Added narrowly scoped **operator-initiated** `ops/postgres/pos-cashier-shifts-admin-grants.sql`. It must not be run until a reviewed environment is provisioned. Migration itself grants no runtime access. Grant script verifies web-admin role independence, restricted functions and direct table access denial.
- Added source-level security regression tests and extended the isolated PostgreSQL RLS/trigger probe to verify the new private functions and idempotency indexes.

**Caveats:** The first operational slice still requires approved register/location provisioning and cashier assignments, cash/stock control testing, an independent operator identity workflow, signed provider settlement, production receipt tax/legal compliance, and fully audited sale/refund transactions. `shop:write` is necessary but never sufficient without an active register-specific assignment. All operations remain disabled until explicit SQL permissions are applied and CI/integration tests pass. Do not merge to OS main or deploy while unverified.

## Staged server-priced checkout, cancellation and fulfillment — 2026-11-10

- Repaired malformed PL/pgSQL dollar-quote delimiters in the earlier POS financial guard migration, which otherwise would have prevented migration execution. The source assertions check balanced delimiters; **real PostgreSQL migration execution still has to be run**.
- Added `20261110154000_PosInventoryReservedCheckout`: a strictly validated basket of 1–30 unique product/variant pairs and quantities 1–99. A dedicated management cashier must have an active organization grant, assigned register and open shift. SQL takes deterministic row locks on location/variant stock, reads current active catalog cost/price from PostgreSQL, rejects client price authority, caps totals, atomically reserves quantities and creates an immutable-intended pending sale with request ID and cart digest. The schema explicitly separates `on_hand` from `reserved` stock.
- **Tax restriction:** The new `pos.checkout_policies` is empty and disabled by default; currently supports only an explicitly reviewed `verified_exempt` treatment. This is **not** a valid general taxable Cyprus checkout. No runtime EXECUTE grant, tax-policy enablement, or location stock configuration is performed.
- Added `20261110155000_PosUnpaidSaleCancellation`: authenticated same-cashier, idempotent cancellation requires an unpaid sale with no pending/captured payments or issued receipt, releases reserved units under row lock, marks sale voided and appends audit. A pending card capture must first receive independent failure resolution, not a cashier cancellation.
- Added `20261110156000_PosReceiptInventoryFulfillment`: the database consumes reserved inventory only after insertion of a verified, reconciled, unique receipt, within the same transaction, ensuring neither overconsumption nor stock loss when issuance rolls back. If reservations are missing or inconsistent, the receipt transaction is rejected. No manual/direct stock decrement endpoint was added.
- Added authenticated `POST /api/admin/pos/cashier/registers/{registerId}/sales/prepare` and `POST /api/admin/pos/cashier/sales/{saleId}/cancel` routes. The JSON contract includes only request/shift IDs, product/variant IDs and quantities; PostgreSQL owns the actual price. **These routes fail closed without a reviewed, separately supplied function grant and tax policy.** They do not charge cards, accept cash, issue receipts, settle payments or create refunds.
- Added source-level regression tests for checkout, cancellation and receipt-bound stock fulfillment. Extended the existing rollback-only isolated PostgreSQL probe for private schema access, reservation tables and new receipt triggers.

### Remaining blockers and non-goals

1. Add reconciled, authorized, evidence-backed **cash tender** operations and Payabl **server-to-server verified capture** only after contract/security review; a checkout reservation is not money received.
2. Implement configurable legally approved VAT/tax treatment and genuine Cyprus receipt/credit-note generation, printable invoice/receipt rendering, reference numbering and accounting export.
3. Add bounded inventory reservations with expiry/recovery for abandoned pending sales and reconciliation of gateway callbacks against previously issued request IDs.
4. Provide operator/location/stock administration and independent permissioning; the new cashier shift screen is not evidence of an available live POS.
5. Run full .NET compilation, PostgreSQL migrations with negative/concurrent transactions, frontend tests, CI and security audit at the exact commit before merging.

This branch remains **draft, unmerged and undeployed**. Do not enable payment capture or apply grants in production.

## Counted cash settlement and shift reconciliation — 2026-11-10

- Added `20261110157000_PosVerifiedCashTender`: a single authenticated SQL transaction that rechecks the active cashier's exact organization, register, and shift, validates a prepared, completely unpaid sale and its stock reservation, and requires *both* explicitly approved checkout-tax and receipt fiscal policies before taking cash. The policy tables are empty/disabled after migration. A non-empty request UUID produces a replay-safe `verification_reference`; only that cashier's exact sale, captured amount and tendered amount may be replayed. The function records the counted cash tendered, net sale amount and change due in EUR cents, appends the audit event and invokes the private receipt finalizer. Receipt finalization and stock consumption occur in **the same database transaction**, so a receipt failure rolls back the cash ledger and inventory as well. An explicit cash tender amount remains a human cashier assertion, **not a card capture**.
- Added manager-only `POST /api/admin/pos/cashier/sales/{saleId}/tender-cash?organization_id=...` to call the above SQL function, but **no runtime EXECUTE grant or UI cash collection button has been enabled**; tax and fiscal approval is required before any real usage.
- Added `20261110158000_PosCashierReconciliationRead` and restricted `GET /api/admin/pos/cashier/shifts/{shiftId}/reconciliation?organization_id=...`. The report checks live cashier assignment, current organization and original shift cashier, then calculates paid/pending sales, issued receipts, verified cash vs card totals, verified cash/card refunds, pending card events, outstanding reservations and mismatched sale/receipt state, with cash expected and variance.
- Added on-demand reconciliation viewing in `AdminPosCashierShiftsPanel.svelte` using strict owner/shift/response checks. Source-level regression tests: `frontend/tests/pos-verified-cash-tender.test.mjs` and `frontend/tests/pos-cashier-reconciliation-read.test.mjs`. The isolated PostgreSQL probe now checks disabled fiscal policies, cash-tender constraints and no PUBLIC function privilege.

**Still not an operational live POS:** cashier/register provisioning, VAT fiscal approval, function execution grants, cash acceptance UI, card confirmation, card returns/refunds, return review, PDF/print receipts and secure replay/concurrency integration tests are not finished. All new SQL is staged with default-deny runtime privileges. Do not use on production, enable payments or merge PR #153 until compiled .NET/PostgreSQL lifecycle and fiscal/security reviews succeed.

## Payabl verification, VAT review, return approvals and print view — 2026-11-10

- `PayablNotificationVerifier.cs`: strict bounded verifier for payabl.'s **simplified notification SHA-256** signature over `transactionid + type + errorcode + timestamp + merchantSecret`, with timing-safe comparison and replay-age limits. It is **not** a live payment status or authorization handler. It does not process card data, call payabl. or update sales. Verified signatures alone are insufficient: `orderid` is not included in that simplified signature; merchant/order/amount/currency binding, provider transaction status lookup and duplicate/out-of-order reconciliation must independently pass before any capture is recorded. The browser return never confirms money received.
- `20261110160000_PosPayablNotificationInbox`: private, RLS-protected pending-recheck inbox for signed callback evidence, with unique transaction/evidence identities, an audited-recheck status field and no cashier/public grants. No webhook endpoint yet; no provider event is allowed to mark a sale paid simply by existing in this inbox.
- `20261110159000_PosCyprusVatCatalog`: organization-specific, effective-dated and versioned VAT treatment definitions for 19%, 9%, 5%, 3%, zero-rated 0% and exempt, requiring reviewed classification/reference and an explicit per-variant assignment. The treatment table is **disabled by default**, does not auto-assign a VAT rate, and does not alter the previous exempt-only disabled checkout. General POS sales are NOT fiscal-ready; assigning a reduced rate or exemption must be justified for each product.
- `20261110161000_PosReturnManagerReview`: a cashier with an assigned live register can request a bounded return against an existing fully paid and receipted sale. The request is idempotent, with original line quantities validated in the underlying trigger. A **different** currently authorized manager must approve or reject; replay is protected and audit events are written. This does NOT contact payabl. or execute a refund. Manager-only admin API routes were added for return request and review; no runtime execution grants.
- `20261110162000_PosProtectedReceiptRead`: an original-cashier-only, scoped private SQL function rechecks the immutable stored receipt hash and sale/receipt identity before returning a snapshot. Read API `GET /api/admin/pos/cashier/receipts/{receiptId}` and Svelte view `/admin/pos/receipts/{receiptId}` display the original recorded itemized receipt and offer explicit browser printing. No new receipt is created by viewing/printing; this is **not** a claim of compliant printed Cyprus tax invoice, and fiscal/business issuer fields require approval.
- Added `frontend/tests/pos-payabl-vat-return-gates.test.mjs` and `frontend/tests/pos-protected-printable-receipt.test.mjs` as structural security/contract checks. Payabl checksum fixture is derived from payabl. published documentation. Real .NET execution tests, PostgreSQL migration/concurrency and end-to-end gateway sandbox tests are pending.

Primary provider sources: https://docs.payabl.com/docs/signature-calculation ; https://docs.payabl.com/docs/refund ; https://docs.payabl.com/docs/integration-steps . Cyprus VAT reference: https://www.gov.cy/mof-tax/documents/syntelestes-f-p-a/ . Do not copy secrets or customer payment-card details into this repository or tests.

**Release blockers:** Real payabl. capture status lookup with merchant credential vault and validated order mapping, refund request+confirmation, original-charge/refund ledger and credit-note issuance, per-line approved VAT arithmetic, fiscal identity/address/numbering and PDF template parity, stock restock policy, tests on disposable database (including concurrency and signed/unsigned spoofed callbacks), exact-sha passing GitHub Actions, and explicit operator sign-off. All financial endpoints and SQL grants introduced here remain default-deny. NEVER deploy to production or merge the draft PR before verification.

## Reviewed pending refund request slice

Migration `20261110163000_PosReviewedRefundRequests` adds a default-deny function to submit an **idempotent pending refund instruction**, only after a sale-linked, receipted return was approved by a different manager. To prevent conflicts of interest, the refund request actor must be different from both the original return requester and the return reviewer. It rechecks the active admin identity and organization, locks the exact return and verified original payment, matches the sale and method, and relies on the existing `pos.guard_refund_amount` trigger to enforce the payment and returned-item value ceilings. The function appends a refund_request audit event. The authenticated `POST /api/admin/pos/cashier/returns/{returnId}/refund-requests` route is mapped but has **no default runtime SQL execution grant**.

This records an instruction with `status='pending'` only: it **does not transfer funds, make a cash payment, contact Payabl, or confirm a refund**. Automatic provider refund request, signature verification, idempotent provider confirmation, credit note, inventory return decision, and cashier disbursement require separate implementation and security validation. Added structural tests `frontend/tests/pos-refund-request-gates.test.mjs` and PostgreSQL default-deny/idempotency assertions in `ops/postgres/pos-cashier-ledger-checks.sql`.
## Integration safety boundary (2026-11-11)

The pre-existing OS POS location/stock/sales schema from PR #152 is **not compatible** with the standalone cashier migration's original duplicate tables. For migration safety, this integration stages cashier tables and functions under `pos_cashier`, references the existing `pos.locations` directory, and orders its migrations after the POS location migrations. The cashier stock reserve is deliberately separate from `pos.location_stock` at this stage. **Do not enable cashier checkout, payment capture, fiscal receipt issuance, refunds, or finance posting in production** until inventory reconciliation, unified location/register setup, fiscal controls, and provider verification are implemented and reviewed end-to-end. Default-deny permissions remain required. This is a private foundation, not a deployed or unified operating POS.
