# CRM · ενιαίες εγγραφές Ακαδημίας (15 Νοεμβρίου 2026)

## Απόφαση

Το ξεχωριστό στοιχείο πλοήγησης «Γραμματεία Ακαδημίας» καταργείται ως ονομασία/ανεξάρτητη ενότητα. Το CRM περιλαμβάνει **Εγγραφές Ακαδημίας**, **Ενδιαφερόμενοι Ακαδημίας** και (μελλοντικά) **Καμπάνιες & παραπομπές**. Ο παλιός σύνδεσμος `/admin/academy-office` διατηρείται για συμβατότητα· υπάρχει μόνο μία οθόνη αιτήσεων.

## Συμπεριφορά αυτής της αλλαγής

- Μία λίστα `academy_intake.registrations`: ηλεκτρονικές και χειροκίνητες αιτήσεις, ξεχωριστή σήμανση προέλευσης, έκδοση κατάστασης και ασφαλής ροή ελέγχου.
- Ο Super Admin Ακαδημίας βλέπει τις δύο πηγές. Ο Academy Manager βλέπει/ελέγχει **μόνο** τις δικές του χειροκίνητες εγγραφές έως ότου υπάρξει ελεγμένη ανάθεση αίτησης σε πόλη/τοποθεσία. Το όριο επιβάλλεται στη SQL `identity.admin_academy_office` (ανάγνωση και αναθεώρηση), όχι μόνο στον browser.
- Χειροκίνητη προσθήκη από αναδιπλούμενη φόρμα, ώστε η εισερχόμενη λίστα να παραμένει κύρια λειτουργία.
- Οι εσωτερικές παραγγελίες παραμένουν διαθέσιμες ως καρτέλα της υπάρχουσας οθόνης, χωρίς μετάπτωση ή διαγραφή δεδομένων.
- Η παλιά `/api/admin/academy/intake` παραμένει διαθέσιμη ως περιορισμένο, μόνο-για-Super-Admin endpoint, αλλά δεν τροφοδοτεί δεύτερο πίνακα στην ίδια οθόνη.
- Το `recorded_by IS NULL` σηματοδοτεί την ηλεκτρονική/εισαγόμενη πηγή. Δεν εμφανίζονται ιατρικά δεδομένα, υπογραφές ή πρωτογενή στοιχεία συναίνεσης στον CRM κατάλογο.

## Τι ΔΕΝ θεωρείται ολοκληρωμένο

Η μετάβαση `under_review → approved` παραμένει **έγκριση αίτησης**, όχι δημιουργία παίκτη. Δεν δημιουργεί `club.players`, δεσμό κηδεμόνα, συνδρομή, λογαριασμό εφαρμογής, χρέωση ή εγγραφή σε τμήμα. Η δημόσια φόρμα εξακολουθεί να είναι ανενεργή από προεπιλογή, έως την ελεγχόμενη ενεργοποίηση των όρων συναίνεσης, κλειδιών κρυπτογράφησης και ασφαλούς rate limiting.

Για την επιθυμητή οριστική ενέργεια **«Επιλογή πόλης → τοποθεσίας → τμήματος → Έγκριση και ένταξη»** απαιτείται ξεχωριστή ελεγμένη, ατομική εντολή backend, με:

1. Σαφή επαλήθευση κηδεμόνα, ιδιωτικών στοιχείων/συναίνεσης, διπλοεγγραφών και readiness του κανονικού ρόστερ.
2. Επιλογή μόνο ενεργών `club.academy_group_location_assignments` στη συγκεκριμένη πόλη/τοποθεσία και επιβολή εξουσιοδότησης πόλης/τοποθεσίας στο SQL transaction. Δεν γίνεται ανάμειξη με πρώτη ομάδα ή άλλη πόλη.
3. Δημιουργία/σύνδεση κατάλληλου `club.players` χωρίς εικονικές τιμές θέσης/αριθμού, membership στο συγκεκριμένο `club.player_academy_groups`, ενημέρωση `onboarded_player_id`, optimistic lock σε `status_version`, append-only audit και ατομικό rollback.
4. Αποτροπή διπλής εκτέλεσης, ασφαλή σύνδεση κηδεμόνων σε ξεχωριστή εξουσιοδότηση, χωρίς αυτόματη χρέωση, μήνυμα ή δημιουργία διαπιστευτηρίων.
5. Πραγματικά PostgreSQL integration tests, stale-session/role-revocation tests και δοκιμές σε απομονωμένο staging.

Δεν υλοποιούμε κουμπί που ισχυρίζεται ότι πρόσθεσε παιδί σε τμήμα χωρίς επαληθευμένη ατομική εντολή και τη σχετική ασφάλεια.

## Έλεγχοι

Η δοκιμή `frontend/tests/public-registration-live-flow.test.mjs` επιβεβαιώνει ότι η ενοποιημένη οθόνη δεν καλεί δεύτερη λίστα, ενώ η μεταγενέστερη migration επιβάλλει το όριο εγγραφών στα δύο SQL σημεία (αναζήτηση/αναθεώρηση). Απαιτείται επιπλέον πραγματικό DB integration/CI πριν από συγχώνευση ή staging activation. Καμία ενέργεια δεν ενεργοποιεί τη δημόσια φόρμα ή αγγίζει την παραγωγή.
